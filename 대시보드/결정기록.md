# 결정기록 — 대시보드

지금 코드가 왜 이렇게 동작하는지 설명하는 운영 결정. 코드 주석에서 옮겼다(2026-10-25 주석 정리). 화면 설계 경위는 CLAUDE.md "대시보드 2단계·3단계"에 있다.

## 읽기 전용·수동 새로고침
- 결정: DB는 db_manager로만 열고 연결마다 read_only로 바꾼 뒤 끝에 rollback한다. MLflow는 sqlite를 mode=ro로 연다. 캐시는 st.cache_data(ttl=300)와 새로고침 버튼(캐시 비우기)뿐이고, 자동 새로고침(st.fragment run_every 등)은 쓰지 않는다. GitHub Actions는 인증 없이 새로고침당 1요청(최근 run 20개)만 한다.
- 이유: 대시보드는 보기 전용이다. 자동 새로고침은 Neon 컴퓨트를 계속 깨워 비용이 든다. 인증 없는 GitHub API 한도는 시간당 60회다.
- 관련 코드: 데이터.query, 파이프라인_상태.mlflow_runs, 파이프라인_상태.github_runs, 운영_대시보드(새로고침 버튼)
- 결정 시점: 2026-10-18

## 사전 예측 판정은 평가일 08:30
- 결정: 운영 행 중 model_version(KST)이 평가일(realized_date) 08:30보다 이른 행만 "운영(사전 예측)", 나머지는 "운영(사후 계산)"으로 나눠 집계한다. 운영 = model_registry.source='live'(시험·과거 백테스트 실행 제외).
- 이유: 보충 실행·백테스트로 장 시작 뒤에 계산된 행은 실시간 예측 평가에 쓰면 안 된다. model_version은 체크포인트 저장 시각이라 실제 저장보다 최대 약 11분 이르므로 09:00 대신 08:30으로 여유를 둔다. created_at은 최초 INSERT 시각이라 덮어쓰기 뒤 값의 계산 시각이 아니다.
- 관련 코드: 데이터.is_pre_prediction, 데이터.operational_records
- 결정 시점: 2026-10-11(원칙), 2026-10-18(화면 적용)

## 패널 C의 RMSE는 종목평균, 불완전한 날은 일별에서 뺀다
- 결정: RMSE는 배포 게이트와 같은 종목평균(종목별 RMSE의 평균)이다. 하루치는 종목당 1행이라 평균 절대 오차와 같다. 행이 90개 미만인 평가일은 "불완전"으로 일별 값에서 빼고, 두 버전이 섞인 날은 "버전 혼재" 칩을 붙인다. 실측은 model_predictions_realized 뷰(예측 기준일 뒤 첫 거래일)로 계산한다.
- 이유: 게이트와 같은 축으로 봐야 비교가 된다. 일부 종목만 있는 날(예: 10/13 경합 사고 12행)은 하루 RMSE가 대표성이 없다.
- 관련 코드: 데이터.tickermean_rmse, 데이터.MIN_ROWS_PER_DAY, 운영_대시보드.day_chips
- 결정 시점: 2026-10-18

## 일별 성능은 하이브리드 ÷ 최선 baseline 비율로 본다
- 결정: 일별 그래프는 "하이브리드 ÷ 최선 baseline"(그날 평균 절대 오차 기준, 1 미만 = baseline 셋을 모두 이김) 비율로 그리고, 점 툴팁에 평균 절대 오차·실현 평균·평균 오차(+ 과대)를 보인다. 평가일별 표는 평균 절대 오차(그날 최저 굵게)와 실현 평균·÷최선 열이다. 여러 날을 묶은 그룹 요약 표는 게이트와 같은 종목평균 RMSE 그대로다.
- 이유: 하루치 종목평균 RMSE는 평균 절대 오차와 같고, 그 크기는 그날 시장 변동을 따라간다(운영 17개 평가일에서 실현 평균과 상관 0.93) — 큰 날은 모델이 잘해도 숫자가 크다. 날짜끼리는 baseline 대비 비율로 봐야 모델이 그날 이겼는지 보인다(예: 10/15는 4.49로 커 보이지만 GARCH 대비 1.07, 10/20은 1.43으로 실제로 크게 졌다). 비교 대상이 그날 가장 잘 맞힌 baseline이라 엄격한 기준이다(게이트도 셋 다 이겨야 통과).
- 관련 코드: 데이터.daily_compare, 데이터.BASELINE_LABELS, 운영_대시보드.render_panel_c
- 결정 시점: 2026-10-25(사람 요청)

## 밝은 테마 고정, 파랑은 데이터 전용
- 결정: 밝은 테마(연회색 배경 + 흰 카드)로 고정하고, 파랑 등 데이터 색은 막대·선에만 쓴다. 상태는 6종(success·running·warning·failure·waiting·skipped)만 쓰고, 색 + 서로 다른 모양의 아이콘 + 글자로 그린다. 상태 글자색은 흰 바탕·칸 배경·페이지 배경 모두에 WCAG 대비 4.5 이상인 진한 변형이다. 아이콘은 글꼴 문자 대신 CSS mask SVG로 그린다.
- 이유: 색만으로 상태를 구분하지 않게 하고, 데이터 색과 상태 색이 섞이지 않게 한다. 문자 아이콘(✓⚠)은 글꼴에 따라 이모지로 그려져 굵기·크기가 들쭉날쭉하다.
- 관련 코드: 테마.STATUS, 테마._ICON_SVG, 테마.status_chip, 테마.show_chart
- 결정 시점: 2026-10-11(사람 결정), 아이콘 통일 2026-10-18

## 격자 사이클과 열 날짜
- 결정: 기록을 "시각 - 12시간의 KST 날짜"(사이클, 경계 매일 12:00)로 묶는다. 모델 버전(UTC)도 KST로 바꿔 같은 규칙을 쓴다. 열 날짜 = 사이클 날짜 = 그 사이클의 수집 대상일(거래일 후보)이다 — 그날 저녁 수집과 다음 날 05:00 실행이 한 열이다(예: 10/23(금) 저녁 수집, 10/24(토) 05:00 예측 → 10/23 열). 실행 날짜(열 + 1일)는 열 머리·칸 툴팁과 표시줄 제목에 적는다. 12:00 전에는 어제 열이 현재 사이클이다.
- 이유: 저녁 Actions 수집·저녁 수동 실행과 다음 날 05:00 예측이 한 흐름이다. 열을 거래일로 부르면 토·일 열이 휴장 열이 되어 달력과 맞는다.
- 경위: 2026-10-18에 열 이름을 아침 05:00 실행 날짜(사이클 + 1일)로 바꿨다가, 일·월요일 열이 휴장으로 보여 헷갈려 2026-10-25에 거래일로 되돌렸다(사람 결정).
- 관련 코드: 파이프라인_상태.cycle_day, 파이프라인_상태.column_day, 파이프라인_상태.cycle_of, 파이프라인_상태.run_day, 파이프라인_상태.today_cycle
- 결정 시점: 2026-10-18, 2026-10-25(열 = 거래일로 되돌림)

## 휴장 열
- 결정: 열 날짜(수집 대상일)가 휴장이면 그 열 전체를 휴장 열로 본다(열 머리 흐림). 휴장 = 토·일(요일로 바로) 또는 평일 공휴일(공휴일 목록 없이 데이터로 증명: 그날 주가·KOSPI 행 없음 + 뒤 거래일 주가 있음 — 다음 거래일 주가가 들어오기 전에는 증명할 수 없다). 휴장 열의 칸은 다음과 같다.
  - ① 수집·② 데이터 반영: 성공·기록 없음 → "휴장"(skipped), 경고·실패(① 로컬 rc≠0 포함, ② 이탈) → "휴장" 경고 칸(원래 판정은 툴팁). ② 정렬 실패·진행 중·조회 실패는 원래 판정 그대로.
  - ③~⑦: 실행이 없으면 "휴장". 실행이 있고 같은 예측 기준일을 앞 실행이 이미 계산했으면 성공·대기 칸만 "재실행"(skipped), 실패·경고·진행 칸은 원래 판정 그대로. 앞 실행이 없으면(보충 실행) 원래 판정.
- 이유: 휴장일에는 새 거래일이 없어 수집할 것도 학습할 이유도 없다(주말 05:00 실행은 금요일 기준일을 다시 계산해 같은 키를 덮어쓴다). 재실행의 예측이 지금 서빙되므로 그 실행의 실패·경고는 가리지 않는다. 휴장 근거가 없으면 원래 판정이라 실패를 휴장으로 덮지 않는다.
- 관련 코드: 파이프라인_상태.holiday_reason, 파이프라인_상태.non_trading_evidence, 파이프라인_상태.column_holiday, 파이프라인_상태._cell_collect, 파이프라인_상태._cell_align, 파이프라인_상태._holiday_run_cells, 파이프라인_상태.earlier_run_for
- 결정 시점: 2026-10-18(①②만, 증명될 때만), 2026-10-25(열 전체 · 토·일은 요일로 · 재실행 표시, 사람 요청)
- 미결: 휴장일 학습 자체를 건너뛸지는 10/26 실행 점검 뒤 정한다(파이프라인 변경, 대시보드는 표시만).

## 늦은 보충 실행은 처리한 기준일 열에 붙인다
- 결정: 실행(MLflow run·로그·모델 버전)은 시각으로 사이클을 정하되, 그 실행이 실제로 처리한 예측 기준일(MLflow 태그 → 로그 [PRICE-ALIGN] 공통 최신일 → 모델 버전의 DB 예측 행)이 그 사이클의 기대 거래일(사이클 날짜 이하 최신 주가일)보다 이르면 그 기준일 열로 옮긴다. 섞인 태그(예: '2026-10-08,2026-10-12')는 가장 늦은 날로 본다. ① 수집은 시각 그대로다.
- 이유: 05:00 정시를 놓치고 다음 날 12:00 이후에 돈 보충 실행이 하루 뒤 열에 붙어, 원래 열은 "기록 없음"으로 보였다(10/14 18:04 실행 = 10/13분, 10/23 12:38 실행 = 10/22분). 주말 재실행은 기준일 = 기대 거래일(금)이라 토·일 열에 남는다.
- 검증: 원본(MLflow sqlite·로그·DB·Actions)에서 따로 만든 열 매칭과 대조해, 실행이 있는 11개 열 모두 기준일 = 그 열의 거래일(불일치 0).
- 관련 코드: 파이프라인_상태.run_column, 파이프라인_상태._mlflow_day, 파이프라인_상태._log_day, 파이프라인_상태._version_day, 파이프라인_상태._version_pd
- 결정 시점: 2026-10-25

## 마지막 열은 다음 날(예정)
- 결정: 격자는 최근 13일 + 다음 날 열(점선 머리)이다. 다음 날 열의 ①~⑦ 기록 없는 칸은 "예정"(waiting, 휴장이면 휴장), ⑧ 튜닝은 주 1회라 그대로 둔다. 표시줄(현재 사이클)은 다음 날 열이 아니라 현재 사이클 열을 읽는다.
- 이유: 다음 실행이 무엇을 할지(정상 수집·학습인지, 휴장인지) 미리 보이게 한다(사람 요청).

- 결정 시점: 2026-10-25

## ⑤ 예측 저장의 덮어씀 판정
- 결정: ⑤ 칸은 그 버전 마지막 기준일의 예측 행 수(100 성공·90 이상 경고·미만 실패)다. 이후 실행이 같은 키를 덮어써 버전 전체 행이 실행 기록(MLflow·로그의 저장 수)보다 적으면 실행 기록 수로 판정하고 "100(덮어씀 88)"처럼 쓴다.
- 이유: model_predictions는 (ticker, target_date) UPSERT라 나중 실행이 행을 가져가면, 정상 저장한 실행이 실패처럼 보인다.
- 상태: 에이전트 판단, 사람 확인 대기. 수동·재시도 실행 표시도 미적용.
- 관련 코드: 파이프라인_상태._cell_save, 운영_대시보드.grid_short

## ⑧ 튜닝은 부모 run 태그만 읽는다
- 결정: ⑧ 칸은 MLflow 실험 주간_튜닝에서 태그 run_kind=tuning_parent인 부모 run만 보고, status와 state 태그(adopted·kept·reverted·none)로 판정한다. 칸 글자는 시작 시각, 결과는 아이콘(↑ 채택 · = 유지 · ↩ 복귀 · □ 기본)이다.
- 이유: 지표 이름에 기대지 않아 튜닝 코드가 지표를 바꿔도 깨지지 않는다. 튜닝 코드가 run_kind·state 태그 이름이나 state 값을 바꾸면 TUNING_STATES와 TUNE_ICONS도 함께 고친다.
- 관련 코드: 파이프라인_상태._cell_tuning, 파이프라인_상태.TUNING_STATES, 운영_대시보드.TUNE_ICONS
- 결정 시점: 2026-10-18

## 백테스트 재생은 DB에 쓰지 않는다
- 결정: 재생 결과는 대시보드/cache/의 parquet·meta.json에만 쓴다. 프로세스의 db_manager.get_db_connection을 read_only 연결로 바꾼 뒤 가격예측 모듈을 import한다. 학습하지 않는다. 서빙 창(split_dataset.build_next_day_merged_window_volatility_hybrid), 예측 순서(창 → float32 → scaler → 모델, store.predict_and_save_for_ticker와 같음), baseline(baselines.compute_ticker_baselines의 next_day), 실측(model_predictions_realized 뷰 SQL)은 운영 코드를 그대로 쓴다. prediction_date마다 가격을 그날까지로 자르고, 체크포인트 split_val_end 이전 날짜는 뺀다.
- 이유: model_predictions는 (ticker, target_date) UPSERT라 재생값을 쓰면 운영 행을 덮어쓴다. 새로 구현하면 운영과 다른 값이 나올 수 있다. 학습·검증 구간 날짜는 표본 밖 성능이 아니다.
- 관련 코드: 백테스트_재생.get_read_only_connection, 백테스트_재생.predict_one, 백테스트_재생.REALIZED_SQL, 백테스트_재생.main
- 결정 시점: 2026-10-18

## 재생은 운영 GARCH 캐시를 읽기만 한다
- 결정: 재생은 운영 GARCH 파라미터 캐시를 garch_read_only=True로 쓴다. 메타에 캐시 fitted_at 범위를 남긴다.
- 한계: 캐시가 30일을 넘기면 만료로 실패한다. 재적합된 뒤에 옛 체크포인트를 재생하면 그 모델이 학습할 때와 다른 GARCH 파라미터로 계산되므로, 재적합 뒤에는 그날 학습된 최신 체크포인트로 다시 만든다.
- 관련 코드: 백테스트_재생.predict_one, 백테스트_재생.main
- 결정 시점: 2026-10-18
